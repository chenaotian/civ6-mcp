# 原版“公平报价”请求

`inspect_game("deal_negotiation", {"target_player": 已遇见玩家编号})` 返回当前原版交易面板实际显示且启用的 `EqualizeDeal` 按钮动作。其标题可能是“你要什么”“你会给我什么”或“让这笔交易公平”，以当前原版按钮文字为准。返回 `deal_equalize` 动作固定绑定当前外交会话编号及完整、安全的本方草案签名。

执行时再次验证当前面板双方、可见按钮及祖先、模态遮挡、v2 公开外交事件所确定的当前会话、草案签名及原版有效性。只发送一次 `DealManager.SendWorkingDeal(DealProposalAction.EQUALIZE, me, target)`；不调用 AI 私有估值接口，不自动接受或重试。原版正处理中的交易、索取、已失败的公平报价、无安全完整草案或缺少必要接口都不会提供请求动作。

提交后通过 `wait_for_change` 或新的正常观察等待原版事件，再读取 `deal_state`。AI 可以拒绝调整；也可能加入新的条款。结果继续经过现有玩家权限过滤，含被过滤条款的报价不能接受，也不输出这些条款的类别、数量、值或指纹。即使返回可接受报价，也必须另行明确执行 `deal_respond`。

观察在 `InGame` 与固定 `DiplomacyDealView` 两个 Lua 上下文依次进行；只有会话、玩家、回合及连接代次一致才发出新观察令牌。按钮通过该固定上下文的 `Controls.EqualizeDeal` 直接确认，未猜测跨上下文控件路径，也不遍历或读取交易正文。一次请求的等待标记引用现有 v2 阶段对象；后续正常公开事件替换该对象后才能重新请求，接受／拒绝所用的阶段退役机制不在此复用。

源码依据：GS `DiplomacyDealView.lua:163–165,343,518–520` 的正常按钮请求；`:420–475,1004–1088` 的有效性及显示条件；`:17–18,3024–3025` 的面板双方公开全局；`DiplomacyDealView_Expansion2.lua:97–105` 的礼物区分。实现复用实际按钮状态，避免根据草案内容猜测按钮可用性。

T126 已在马里正常交易场景验证询价、完整报价、明确接受和资源到账，证据见下文。其他报价分支仍需各自验证；不把请求已提交当成报价已经更新或成交。

## 草案编辑后的原版界面刷新

T124 固定只读诊断确认了一个具体状态：面板、双方、父级和会话都匹配，没有模态遮挡或未处理请求，原版 `EqualizeDeal` 自身却处于隐藏状态，捕获阶段为 `REJECTED`。这不是按钮可见性过滤误判。此前类型化草案编辑只修改 working deal，漏掉原版编辑后刷新界面的步骤。

`deal_clear`、`deal_remove_item`、`deal_add_item`、`deal_add_war` 现在在固定 `DiplomacyDealView` 上下文执行原有编辑检查和操作；提交后仅在同一可见面板、同一对手和同一会话仍成立时调用原版 `UpdateDealPanel(g_LocalPlayer)`，再调用 `UpdateProposedWorkingDeal()`。前者按原版逻辑更新界面，后者自行决定是否发送正常 `INSPECT`。不会直接设置按钮显隐、读写私有局部变量、自行计算 AI 价格或接受交易。

依据为 GS `DiplomacyDealView.lua:182–196,818–828,1296–1297,1380–1381,1626–1628` 及 `DiplomacyDealView_Expansion2.lua:95–96`。这两项原版回调必须存在且界面身份已核实，才会提交编辑；过程中界面或会话改变则不刷新另一个会话。刷新／检查可能异步更新报价，仍须重新观察，`submitted` 不保证交易内容保持不变。T126 新的正常编辑场景已验证刷新后原版询价按钮出现。

刷新开始时暂时禁止回应旧阶段的 `INCOMING` 副本，避免原版界面已经重置为待检查、桥接器却尚未收到新事件的短暂窗口。该保护只保存旧阶段对象引用，不把阶段设为 inactive，也不写入猜测的报价动作；正常公开回复替换阶段对象后解除，仍允许继续编辑草案。
